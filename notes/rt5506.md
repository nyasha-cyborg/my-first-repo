# The RT5506 headphone amplifier

Written 2026-10-17, after `/etc/RT5506` came out of the ROM's system partition
(see [`vendor-partition.md`](vendor-partition.md) for the extraction). This is
the last thing standing between the headphone path and audio, and it is much
less of a wall than it first appeared.

## What it is, and why it matters

The RT5506 sits on the headphone path and **mainline has no driver for it**.
The shipped kernel has a full one — `rt5506_probe`, `set_rt5506_amp`,
`set_rt5506_hp_en`, `rt5506_set_gain`, `rt5506_volume_ramp`,
`rt5506_headset_detect`, with two GPIOs and an LDO — so the rt5677's own output
is not what reaches the jack. Without this driver the headphone path has
nothing to drive it, which makes it the blocker, not the rt5677.

## The tuning is a text file

The reason this was expected to be hard is that the amplifier's acoustic
tuning was believed to live inside a compiled Android HAL. It does not. It is
`/etc/RT5506`, plain text, 318 lines, and it is a register table:

```
__TABLE_START__
# …
#init
SECTION_START
MODE 00
0x00, 0xC0,
0x81, 0x30,
…
SECTION_END
…
__TABLE_END__
```

`MODE <nn>` names a section and each following line is a register/value pair
with an optional trailing comment — several of which are explanatory, e.g.
`0x93, 0xAD,#de -pop noise enlarge CP Freq`. There are **21 modes**:

| Mode | Name |
|---|---|
| 00–02 | `init`, `mute`, `off` |
| 03 | `playback` |
| 04–11 | `playback_8_ohm` … `playback_1k_ohm` — one per headphone impedance |
| 12–16 | `voice`, `TTY`, `FM`, `Ring`, `MFG` |
| 17–18 | Beats Effect on, split by impedance |
| 19–20 | Mono headset, Beats off and on |

Some lines in mode 00 are commented out with a leading `#`, which reads as the
build having *disabled* them rather than as decoration — they are still present
in the file, so a transcription has to respect the distinction rather than
strip it.

So a driver is transcribing a known table, not reverse-engineering one. The
table header dates it `RT5506_20140708_fix_1X_mode`, and several comments end
`# modify for C.` or `# new for C.`, suggesting revision letters of the part.

## Answers: it is an analog-side amp with I2C control, and the routing was right

The question posed here first was whether the part takes analog or I2S input,
because that decides both the driver's shape and whether the rt5677 card's
headphone routing is correct. The downstream machine driver answers both.

**Routing — the committed one is right.** `flounder_audio_map` in
`tegra_rt5677.c`:

```c
{"Headphone Jack", NULL, "LOUT1"},
{"Headphone Jack", NULL, "LOUT2"},
```

That is the same connection the card here makes, straight from the codec's line
outputs to the jack. There is no DAPM route through the RT5506.

**The part is not a DAI at all.** It appears in the machine driver only as:

- kcontrols — `tegra_rt5677_rt5506_gain_set` calling `rt5506_set_gain()`, and a
  register-dump control;
- an event handler on the jack widget.

So it is not a codec, and not on any DAI link. In mainline terms it is a
component with **no DAI** — an analog amplifier with I2C control sitting
electrically after `LOUT1`/`LOUT2`.

## What actually turns it on

The `Headphone Jack` widget carries the event callback, and the sequence is
explicit — including a delay that looks load-bearing:

```c
SND_SOC_DAPM_HP("Headphone Jack", tegra_rt5677_event_headphone_jack),

case SND_SOC_DAPM_POST_PMU:
        /* set hp_en low and usleep 10 ms for charging */
        set_rt5506_hp_en(0);
        usleep_range(10000,10000);
        set_rt5506_amp(1, 0);
        break;
case SND_SOC_DAPM_PRE_PMD:
        set_rt5506_amp(0, 0);
        break;
```

Note `set_rt5506_hp_en(0)` — low, not high — and the 10 ms charge before the amp
is enabled. Whatever a driver does here, that order and timing is the one the
hardware shipped with; a comment even mentions a 900 ms depop that is commented
out, so the sequence was tuned rather than derived.

## What a driver would involve

Smaller than it looked, now that the part is understood. It is not a codec, so
there is no DAI, no PCM and no hw_params — a handful of register writes behind a
component with no DAI, plus an enable hook.

- an I2C regmap client at `rt5506@52` on `i2c@7000c400`, the address the port's
  tree already carries;
- the mode table transcribed from `/etc/RT5506`, with mode selection — either a
  control, or automatic from the impedance the part measures;
- `set_rt5506_amp()` and `set_rt5506_hp_en()` equivalents, wired to the headphone
  jack's power-up and power-down, preserving the low-then-delay-then-enable order
  above;
- the `rt5506-enable` and `rt5506-power-en` GPIOs, both still outstanding, plus
  the LDO whose `ldoen` state the shipped driver logged;
- the gain control, if it is worth exposing as a kcontrol rather than fixed.

One consequence for the audio work: because the amplifier is not on a DAI link,
the rt5677 card does not need changing to accommodate it. What it needs is an
enable hook, which is a machine-level concern in the same way the downstream
event handler is.

None of this has been started, and none of it has run on hardware.
