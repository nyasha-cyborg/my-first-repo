# The RT5506 headphone amplifier

Written 2026-10-17, after `/etc/RT5506` came out of the ROM's system partition
(see [`vendor-partition.md`](vendor-partition.md) for the extraction). This is
the last thing standing between the headphone path and audio, and it is much
less of a wall than it first appeared.

## What it is, and why it matters

The RT5506 sits on the headphone path and **mainline has no driver for it**.
The shipped kernel has a full one — `rt5506_probe`, `set_rt5506_amp`,
`set_rt5506_hp_en`, `rt5506_set_gain`, `rt5506_volume_ramp`,
`rt5506_headset_detect`, with two GPIOs and an LDO — so the rt5677's own output
is not what reaches the jack. Without this driver the headphone path has
nothing to drive it, which makes it the blocker, not the rt5677.

## The tuning is a text file

The reason this was expected to be hard is that the amplifier's acoustic
tuning was believed to live inside a compiled Android HAL. It does not. It is
`/etc/RT5506`, plain text, 318 lines, and it is a register table:

```
__TABLE_START__
# …
#init
SECTION_START
MODE 00
0x00, 0xC0,
0x81, 0x30,
…
SECTION_END
…
__TABLE_END__
```

`MODE <nn>` names a section and each following line is a register/value pair
with an optional trailing comment — several of which are explanatory, e.g.
`0x93, 0xAD,#de -pop noise enlarge CP Freq`. There are **21 modes**:

| Mode | Name |
|---|---|
| 00–02 | `init`, `mute`, `off` |
| 03 | `playback` |
| 04–11 | `playback_8_ohm` … `playback_1k_ohm` — one per headphone impedance |
| 12–16 | `voice`, `TTY`, `FM`, `Ring`, `MFG` |
| 17–18 | Beats Effect on, split by impedance |
| 19–20 | Mono headset, Beats off and on |

Some lines in mode 00 are commented out with a leading `#`, which reads as the
build having *disabled* them rather than as decoration — they are still present
in the file, so a transcription has to respect the distinction rather than
strip it.

So a driver is transcribing a known table, not reverse-engineering one. The
table header dates it `RT5506_20140708_fix_1X_mode`, and several comments end
`# modify for C.` or `# new for C.`, suggesting revision letters of the part.

## The question that comes before the driver

**Is the RT5506 an analog amplifier or a codec?** It changes the shape of
everything:

- If it takes **analog** input, it has no I2S DAI. In ASoC terms it is not a
  codec at all — it is an `aux_dev`, or a plain component with no DAI, sitting
  between the rt5677's `LOUT1`/`LOUT2` and the jack.
- If it takes **I2S**, it is a codec with its own DAI and a second I2S link.

This is not a detail to defer, because it also questions the rt5677 card already
committed. That card routes `"Headphone", "LOUT1"` and `"Headphone", "LOUT2"`,
i.e. straight from the codec to the jack. If the audio actually goes
`LOUT → RT5506 → jack`, that routing is wrong: it connects the jack to a line
output while the real path runs through an amplifier that nothing is driving.

Nothing read so far settles it. The mode names point both ways — `playback_1k_ohm`
and `headset_detect` suggest a headphone amplifier with its own output stage,
which is consistent with analog in, while the register count is high enough for a
DSP-bearing part. **This should be answered before writing the driver**, and the
downstream `tegra_rt5677.c` machine driver, which drove the RT5506 from its own
`spk`/`hp` paths, is the place to look.

## What a driver would involve, once that is settled

- an I2C regmap client at the address the port's tree already has, `rt5506@52`
  on `i2c@7000c400`;
- the mode table transcribed from `/etc/RT5506`, with mode selection — either
  a control, or automatic from the impedance the part measures;
- `rt5506-enable` and `rt5506-power-en` GPIOs, both outstanding, plus the LDO
  whose `ldoen` state the shipped driver logged;
- if it turns out to be analog-only: a component with no DAI, and a corrected
  rt5677 card whose headphone route goes through it.

None of this has been started, and none of it has run on hardware.
